# Level 6 Monthly Readiness Summary — Schema & Provenance (OM-2)

> Operational maturity documentation. The summary is **advisory reporting**:
> it is never a qualification gate, never read by any qualification
> calculation, and never changes resource gates, deployment decisions, or
> thresholds. Zero LLM inference; standard library only (ADR-0012).

## 1. What it is

`readiness-summary-YYYY-MM.json` — one deterministic, machine-readable
readiness record per calendar month, generated by the existing readiness
cron (first successful observer run that finds the month's record missing).
Implemented in `bootstrap/level6-readiness-check.py` (`month_key`,
`monthly_summary_due`, `write_monthly_summary`, called from `main` under
`--notify`). Written to `~/.infrastructure-platform/level6-readiness-telemetry/`
(local ignored state — never committed, never inside the repo).

## 2. Scheduling architecture

- **Scheduler:** the existing readiness cron (`level6-readiness-check.sh
  --notify`, daily 09:17 local). No new scheduler introduced.
- **First-of-month semantics:** the daily cron checks
  `monthly_summary_due()`; the month's record is written on the first run
  for which it does not exist, then never again that month.
- **Idempotency:** existence of `readiness-summary-YYYY-MM.json` suppresses
  rewrites — no duplicate records, previous months never overwritten.
- **Missed-run behavior (self-heal):** if the host is down for the first
  runs of a month, any later run in that month writes the summary reflecting
  the best evidence available at write time; `evaluated_at` +
  `generated_by_git_head` prove exactly when and from what revision it was
  produced. No backfill of prior months.
- **Atomicity:** write goes to `<path>.tmp` then `os.replace` — a partial
  record is never visible as a summary, and a failed generation leaves no
  `.tmp` residue and never affects the observer's exit code.
- **Timezone:** month keys are UTC (`%Y-%m`), stable regardless of host TZ.

## 3. Schema (summary_schema_version 1.0.0)

| Field | Meaning |
|---|---|
| `report_class` | Constant `"READYNESS_SUMMARY"` — provenance marker distinguishing it from scheduled qualification evidence |
| `summary_schema_version` | `"1.0.0"` |
| `evaluated_at` | Generation timestamp (UTC) — the execution time of this record |
| `evidence_window_start` / `_end` | Start/end of the contributing evidence window (first/last scheduled record `start_time`) |
| `weeks_accumulated` | Evidence window length in weeks |
| `scheduled_runs` / `machinery_drill_runs` | Counts by trigger class — drills (any non-`periodic-level6` trigger) are excluded from all qualification math |
| `pass` / `fail` / `blocked` | Scheduled-record outcome counts |
| `pass_rate_excluding_blocked` | PASS / (PASS+FAIL+errors) over scheduled records only; `null` when not evaluable |
| `criteria` | Per-criterion boolean matrix (below) |
| `readiness` | `READY` / `NOT_READY` / `ERROR` — interpretation, never a gate |
| `source_evidence_sha256` | SHA-256 over the concatenated bytes of every contributing record file, in run order (verifiable independently: `cat <files> | shasum -a 256`) |
| `source_evidence_runs` | Inventory: `run_id` + `file` for each contributing record |
| `readiness_evaluator` | Generator identity (`bootstrap/level6-readiness-check.py`) |
| `git_head` | Repo revision the evidence window ends against |
| `generated_by_git_head` | Repo revision of the generator run (execution lineage) |
| `generation_trigger` | `readiness-cron-first-of-month` |
| `llm_inference_required` | Always `0` |

## 4. Per-criterion matrix (`criteria`)

Mirrors the Level 7 entry criteria in `level6-readiness-observer.md`:

| Key | True when |
|---|---|
| `history_weeks_met` | evidence window ≥ 4 weeks |
| `pass_rate_excluding_blocked_met` | pass rate ≥ 90% (BLOCKED excluded, drills excluded) |
| `failure_recovery_verified` | every observed FAIL followed by a later scheduled PASS |
| `missed_windows_explained` | every `scheduler_missed_window` field recorded (presence = explained, per observer contract) |
| `fleet_incidents_zero` | no `protected_fleet_check != "yes"` record |
| `comparison_stable` | no comparison errors, ≥ 2 runs |
| `runner_version_change_verified` | ≥ 2 distinct runner versions in window |
| `evidence_survived_reboot` | any record whose file mtime predates last boot still readable |

`readiness = READY` iff all criteria true; otherwise `NOT_READY` with the
matrix showing which. `ERROR` = all evidence malformed/inaccessible —
the summary is still produced honestly with zero counts and empty-hash
provenance (SHA-256 of the empty input), never fabricated values.

## 5. Provenance methodology

Two distinct layers:

1. **Evidence provenance** — `source_evidence_sha256` + `source_evidence_runs`
   bind the summary to the exact bytes of the contributing L6 records;
   independently verifiable against `docs/15-reproducibility/periodic/`.
2. **Execution provenance** — `evaluated_at`, `generated_by_git_head`,
   `generation_trigger` bind the summary to the moment and revision that
   produced it.

## 6. Historical compatibility

Summaries are new artifacts in a separate directory; the evidence loader
scans only `docs/15-reproducibility/periodic/validation-*.json`, so a
summary can never enter qualification counts (test-enforced:
`test_25_summary_never_enters_qualification`). Historical L6 records are
untouched; older summaries are never rewritten; missing summary months are
acceptable (self-healing generation), and their absence is never interpreted
as a qualification event.

## 7. Relationship to qualification

The summary is a **report about** qualification evidence, not a source of
it. It changes no thresholds, no gates, no pass-rate math. Machinery-drill
records remain excluded from qualification (OM-1) and appear only in the
`machinery_drill_runs` count.
